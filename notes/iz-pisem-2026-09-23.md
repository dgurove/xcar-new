# «Из писем»: одна карточка на ТС, три вида — 23.09.2026

## Что было

Кандидат из письма (`mail_candidates`) склеивался только по точной строке
номера убытка. Шесть писем по одной машине — шесть карточек, когда номер
написан по-разному (`677209-2026` / `677209/2026`), когда номера в письме
нет, а есть VIN или госномер (карточка на каждое письмо), когда пересылки
приходят разными ветками. «Завести» привязывало одну ветку — фото из
остальных писем не подтягивались. Экраны «Из писем» на стоянке и в CRM были
разными и не знали трёх видов, сортировки и фильтров.

## Что стало

- **Тождество ТС в почте** — `mail_candidates.key`: `code:{Code::key}` →
  `vin:` → `plate:` → `thread:`; письма — пивот `mail_candidate_messages`,
  `messages_count`, `last_message_at`, `vendor_id` (для фильтра).
  `Candidate::identities($fields, $threadId)` — тождества письма по силе,
  `allIdentities()` — кандидата (поля + ветки всех писем), `strongest()`.
- `ExtractCandidate`: открытые кандидаты scope'а (их десятки) сверяются в PHP
  по пересечению тождеств; письмо ложится в пивот, поля дописываются
  (старое важнее, свежее — в `proposed`), ключ поднимается до сильнейшего.
  Порядок писем не важен: сначала VIN-письмо, потом с номером — ключ всё равно
  `code:`. ТС уже есть по номеру, VIN или госномеру — кандидата нет, ветку
  привяжет `LinkThread::auto`. Telegram владельцу — только на новую ТС.
- Миграция `2026_09_23_100000_mail_candidates_groups` заполняет ключи и
  сливает дубли среди ждущих (в самого раннего, письма переезжают).
- Оба `PromoteCandidate` привязывают **все** ветки; если ТС (не выданная и не
  отменённая) / предложение (не архив) с тем же убытком, VIN или госномером
  уже есть — второго не создают, письма к нему; на стоянке тогда ведёт на
  ТС («Письма привязаны к ТС»), не на заявку.
- Один контроллер `Admin\CandidateController` (`$scope`, `$base`, `$mail`),
  `ParkCandidateController` наследует и переопределяет только `promote`.
  Один экран `mail/candidates/index` + окошко `peek` со списком писем
  (`x-mail.letters`); карточка `x-mail.candidate-card` (заглушка вместо кадра,
  чип «N писем», вложения), строка `x-mail.candidate-row`. Сортировки: свежие
  письма, дольше ждут, по сроку ответа (`extracted->answer_by`). Фильтры: `q`
  по номеру/VIN/госномеру/теме, вендор. «Завести» из окошка уходит на
  страницу (`data-turbo-frame="_top"`), остальное — в окошко.
- `/requests`: `ListView::paginate`, три вида (`x-park.request-card` поверх
  `x-park.card` с `action`, `x-park.request-row`, окошко `/requests/{id}/peek`
  — действия ссылками на страницу заявки), фильтры `q`, `vendor`, `yard`,
  `mine`, сортировка «По типу».
- Почта стоянки: `POST /mail/{thread}/read` (свайп «прочитано» бил в 404),
  пресет «По ТС» вместо «По предложениям» (`MailController::presets()`),
  память списка `park-mail` отдельно от CRM.

## Как проверялось

IMAP локально не работает — письма заводились в tinker (`Message::create` +
`ExtractCandidate::handle`): четыре письма об одной машине (номер, номер в
другом написании, только VIN, только госномер с пробелами) → один кандидат
с двумя письмами (письмо с дефисами без VIN разбор не считает заявкой, номер
с пробелами `PLATE` не ловит — как и раньше); «Завести» → одна ТС, обе ветки
с `vehicle_id`; следующее письмо по ней кандидатом не стало и привязалось;
кандидат по уже заведённой ТС — «Письма привязаны к ТС».
